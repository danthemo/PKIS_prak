# Версионирование

## Общие правила

API системы ТОиР версионируется через путь: `/api/v1`. Все endpoint, DTO и коды ошибок внутри этой версии должны сохранять обратную совместимость.

Внутренние библиотеки и сервисы используют формат `MAJOR.MINOR.PATCH`:

- `MAJOR` меняется при ломающих изменениях;
- `MINOR` меняется при добавлении совместимой функциональности;
- `PATCH` меняется при исправлениях без изменения контрактов.

Миграции БД версионируются датой и порядковым номером в формате `yyyyMMdd_NNN_description.sql`. OpenAPI фиксируется отдельным файлом для каждой версии API, например `openapi-v1.yaml`.

## Таблица совместимости изменений

| Тип изменения | Пример | Ломающее или неломающее | Правило выпуска |
| --- | --- | --- | --- |
| Добавление необязательного поля ответа | `RequestDto.priorityComment` | Неломающее | Выпускается внутри `/api/v1`, обновляется OpenAPI. |
| Удаление поля ответа | Удаление `RequestDto.status` | Ломающее | Требует новой версии API `/api/v2`. |
| Переименование поля | `equipmentId` в `assetId` | Ломающее | Требует новой версии API или периода двойной записи/чтения. |
| Добавление нового endpoint | `GET /api/v1/equipment` | Неломающее | Выпускается внутри `/api/v1`, добавляется контрактный тест. |
| Изменение значения статуса | `IN_PROGRESS` в `ACTIVE` | Ломающее | Требует анализа клиентов и новой версии API. |
| Изменение HTTP-кода ошибки | `409` на `422` для конфликта статуса | Ломающее | Требует новой версии API или отдельного совместимого режима. |
| Добавление nullable-колонки | `audit_log.trace_id` | Неломающее | Выпускается миграцией с проверкой обратной совместимости. |
| Добавление обязательного поля запроса | `CreateRequestRequest.assetCode` | Ломающее | Требует новой версии API или временного значения по умолчанию. |
