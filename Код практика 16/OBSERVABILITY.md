# Наблюдаемость

## Структурированные логи

Каждая бизнес-операция и ошибка должны логироваться в структурированном виде. Минимальный набор полей:

- `timestamp`;
- `level`;
- `traceId`;
- `userId`;
- `role`;
- `operation`;
- `entityType`;
- `entityId`;
- `result`;
- `durationMs`.

Поле `traceId` передается через входящий запрос, создается при отсутствии и возвращается клиенту в каждом ответе.

## Уровни логирования

- `Information` используется для успешных операций, отклоненных валидацией запросов и штатных бизнес-событий.
- `Warning` используется для отказов доступа, конфликтов состояния и подозрительных повторов операций.
- `Error` используется для инфраструктурных ошибок, ошибок записи аудита и необработанных исключений.

## Метрики

- `http_requests_total` — количество HTTP-запросов по endpoint, методу и статусу.
- `http_request_duration_ms` — длительность HTTP-запросов.
- `db_query_duration_ms` — длительность запросов к PostgreSQL.
- `business_conflicts_total` — количество конфликтов состояния заявок и нарядов.
- `validation_errors_total` — количество ошибок валидации входных DTO.
- `audit_write_errors_total` — количество ошибок записи в `audit_log`.
- `idempotency_replays_total` — количество повторных идемпотентных операций.

## Минимальные алерты

- Рост 5xx больше 2% за 5 минут.
- p95 HTTP-запросов больше 1000 мс.
- p95 запросов к БД больше 500 мс.
- `audit_write_errors_total` больше 0.
- Резкий рост `409 STATE_CONFLICT`.
- Истечение TLS-сертификата менее чем через 14 дней.
